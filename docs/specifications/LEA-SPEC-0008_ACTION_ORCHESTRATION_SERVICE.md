# Action Orchestration Service Specification

## Status

| Item | Value |
|---|---|
| Status | Accepted |
| Requires Review | No |
| Implementation | Complete |
| Test Status | Passed - 419 tests |

## 1. Purpose

This specification defines the deterministic action orchestration service for
LEA.

The orchestration service coordinates the existing action proposal,
validation, confirmation, execution and audit components into explicit
application workflows.

It does not add new domain actions, background execution, plugin discovery,
scheduling, retries or autonomous approval.

## 2. Scope

Milestone 1.7 shall provide:

- one deterministic orchestration service;
- explicit proposal submission;
- validation through `validate_proposal_data`;
- confirmation-policy application through `apply_confirmation_policy`;
- explicit confirmation-decision application through
  `apply_confirmation_decision`;
- approved-only execution through `execute_action`;
- audit-event creation through the existing audit factories;
- append-only audit persistence through an injected audit sink;
- structured immutable orchestration results;
- safe failure containment at orchestration boundaries;
- explicit dependency injection;
- no hidden global state;
- no filesystem path selection inside the service;
- no AI model calls inside the deterministic orchestration layer.

## 3. Non-goals

Milestone 1.7 shall not provide:

- domain-specific business actions;
- background workers;
- queues;
- schedulers;
- automatic retries;
- concurrent execution;
- distributed locking;
- plugin discovery;
- configuration-file loading;
- command-line user interaction;
- Telegram or LAN messaging;
- model inference;
- autonomous confirmation;
- automatic approval;
- persistent proposal repositories;
- audit repair;
- HMAC or digital signatures;
- rollback of external side effects.

## 4. Design principles

The orchestration service shall be:

- deterministic;
- dependency-injected;
- explicit about every operation;
- independent of storage paths;
- independent of user-interface adapters;
- independent of AI models;
- safe against execution before approval;
- auditable;
- testable without filesystem or network access.

## 5. Existing components

The service shall compose existing accepted components rather than duplicate
their behaviour.

The current proposal contract is defined by `ActionProposal` in
`lea.actions.models`.

The current deterministic workflow functions include:

- `validate_proposal_data`;
- `transition_proposal`;
- `evaluate_confirmation`;
- `record_confirmation`;
- `apply_confirmation_policy`;
- `apply_confirmation_decision`;
- `execute_action`.

The current audit factories include:

- `audit_proposal_created`;
- `audit_validation_completed`;
- `audit_transition_result`;
- `audit_confirmation_evaluation`;
- `audit_confirmation_record`;
- `audit_confirmation_policy_application`;
- `audit_confirmation_decision_application`;
- `audit_action_execution`.

The orchestration service shall not weaken, bypass or duplicate these
contracts.

## 6. Public contracts

### 6.1 ActionOrchestrator

The implementation shall provide an `ActionOrchestrator` class.

It shall receive all external dependencies explicitly during construction.

Initial dependencies shall include:

- an `ActionHandlerRegistry`;
- an audit sink;
- a timezone-aware UTC clock;
- an audit-event identifier source.

Additional narrow callable dependencies may be injected when this improves
testability without duplicating existing domain contracts.

The orchestrator shall call the existing deterministic workflow functions
rather than replace them with parallel validator, confirmation or executor
implementations.

### 6.2 Audit sink protocol

The orchestration layer shall depend on an audit sink abstraction rather than
a concrete JSONL store.

The minimum contract shall accept one immutable `AuditEvent`.

The sink may be backed by:

- the plain append-only `JsonlAuditStore`;
- the integrity-enabled `IntegrityJsonlAuditStore`;
- an in-memory test double;
- a future service adapter.

The orchestrator shall not inspect or manipulate the sink's filesystem path.

### 6.3 Clock protocol

The clock shall return a timezone-aware UTC `datetime`.

Public orchestration methods shall not call `datetime.now()` directly.

### 6.4 Audit-event identifier source

The identifier source shall return canonical UUID strings for audit events.

Public orchestration methods shall not call random UUID generation directly.

Proposal identifiers remain part of the supplied `ActionProposal` contract and
shall not be regenerated by the orchestrator.

### 6.5 Structured result

Each public orchestration operation shall return a structured immutable result.

The result shall identify, where applicable:

- the resulting proposal;
- the operation outcome;
- the validation result;
- the confirmation-policy application result;
- the confirmation-decision application result;
- the action-execution result;
- the audit events successfully persisted;
- a structured orchestration issue.

The result shall use explicit optional fields rather than unstructured
dictionaries.

### 6.6 Operation outcome

The operation outcome shall be represented by a stable `StrEnum`.

Initial outcomes shall distinguish at least:

- submitted;
- validation_failed;
- confirmation_required;
- approved;
- rejected;
- cancelled;
- execution_succeeded;
- execution_failed;
- audit_failed;
- invalid_operation.

Exact member names may be refined during implementation, but outcomes shall
remain stable, serialisable and non-ambiguous.

## 7. Submission workflow

The proposal-submission operation shall:

1. receive an immutable `ActionProposal`;
2. serialise it through its existing canonical contract;
3. validate the serialised data through `validate_proposal_data`;
4. create and persist `audit_proposal_created`;
5. create and persist `audit_validation_completed`;
6. stop with a structured validation failure when validation fails;
7. apply confirmation policy through `apply_confirmation_policy` when
   validation succeeds;
8. create and persist
   `audit_confirmation_policy_application`;
9. return the resulting proposal and structured orchestration result.

Submission shall never call `execute_action`.

The orchestrator shall not create an additional transition event when the
existing confirmation-policy application audit event already contains the
canonical transition result. Duplicate audit representations shall be avoided.

## 8. Confirmation workflow

The confirmation operation shall:

1. receive the current immutable `ActionProposal`;
2. receive an explicit `ConfirmationDecision`;
3. receive the human actor and optional reason required by the existing
   confirmation contract;
4. apply the decision through `apply_confirmation_decision`;
5. create and persist `audit_confirmation_decision_application`;
6. return a structured result.

The orchestrator shall never fabricate human approval.

High- and critical-risk proposals shall continue to require explicit human
confirmation according to the accepted confirmation policy.

The orchestrator shall not create duplicate standalone confirmation or
transition events when the existing decision-application audit event already
contains those canonical records.

## 9. Execution workflow

The execution operation shall:

1. receive the current immutable `ActionProposal`;
2. invoke `execute_action` with the injected `ActionHandlerRegistry`;
3. supply explicit start and completion timestamps from the injected clock;
4. preserve the existing approved-only execution boundary;
5. preserve the existing `approved → executing → succeeded` or
   `approved → executing → failed` progression;
6. create and persist `audit_action_execution`;
7. return the final proposal and structured action-execution result.

Execution shall not occur for proposals in any non-approved state.

The existing `ActionExecutionResult` contains its start transition, completion
transition and execution record. The orchestrator shall not duplicate these as
additional audit events unless the accepted audit specification is extended
later.

## 10. Audit ordering

Audit events shall be persisted in the deterministic order in which each
orchestration operation creates them.

The initial expected order is:

### Submission

1. proposal created;
2. validation completed;
3. confirmation policy applied, when validation succeeds.

### Confirmation

1. confirmation decision applied.

### Execution

1. action execution result.

Composite workflow audit events shall preserve their embedded canonical
records and transitions.

The orchestrator shall not reorder audit events by timestamp or event type.

## 11. Audit persistence behaviour

Audit events shall be serialised and created before they are passed to the
audit sink.

Each successful sink call shall be recorded in the orchestration result's
persisted-events tuple.

When a later sink call fails, the result shall distinguish already persisted
events from the event that failed.

The orchestrator shall not claim that all planned audit events were persisted
when only a prefix was written.

## 12. Audit failure behaviour

Audit persistence can fail after an immutable workflow operation has already
produced a new value.

The implementation shall fail closed and return a structured audit failure.

It shall not:

- silently continue;
- retry automatically;
- overwrite existing audit history;
- repair the audit file;
- claim cross-system atomicity.

Milestone 1.7 cannot provide atomicity between workflow values, audit
persistence and external handler side effects.

This limitation shall be documented explicitly.

## 13. Side-effect boundary

The orchestrator itself shall perform no external side effects other than
calling its injected dependencies.

External action effects remain contained within handlers registered in the
injected `ActionHandlerRegistry`.

The orchestration layer shall not:

- open network connections;
- select runtime paths;
- read environment variables;
- discover plugins;
- invoke shell commands directly;
- communicate with users directly.

## 14. Determinism

Given equivalent immutable inputs and equivalent deterministic dependencies,
the orchestrator shall produce equivalent workflow decisions and result
structures.

Clock values and generated audit-event identifiers shall come from injected
deterministic sources in tests.

No public orchestration method shall call the system clock or random UUID
generation directly.

## 15. Error containment

Expected contract, workflow and audit failures shall be represented through
structured immutable results.

Unexpected exceptions from injected audit sinks, clocks or identifier sources
shall be converted into stable orchestration issues.

Handler exceptions remain contained by the existing `execute_action`
boundary.

The original exception shall be preserved as the cause where appropriate for
diagnostics.

Sensitive exception details shall not be copied blindly into user-facing
messages.

## 16. Immutability

New public orchestration contracts shall use immutable dataclasses with slots.

Nested mutable data shall not be exposed through public result objects.

Existing immutable proposal, confirmation, execution and audit contracts shall
be preserved.

## 17. Public API

The orchestration package shall expose only intentionally supported names.

Every module-level `__all__` list shall contain quoted strings with four-space
indentation.

New public API names shall be documented and covered by tests.

## 18. Testing requirements

Automated tests shall cover at least:

- successful proposal submission;
- failed proposal validation;
- confirmation not required;
- confirmation required;
- approval application;
- rejection application;
- cancellation application;
- execution blocked before approval;
- successful approved execution;
- failed approved execution;
- handler exception containment through `execute_action`;
- deterministic audit-event ordering;
- no duplicate transition or confirmation audit events;
- audit sink failure during proposal-created persistence;
- audit sink failure after a partially persisted submission;
- audit sink failure during confirmation;
- audit sink failure during execution;
- injected clock use;
- injected audit-event identifier use;
- no direct filesystem access;
- no direct system-clock access;
- no direct UUID generation;
- immutable result contracts;
- no mutation of supplied proposals;
- no automatic approval;
- no execution during submission;
- no destructive audit operations.

The complete repository quality gate shall pass before Milestone 1.7 is marked
complete.

## 19. Documentation requirements

Completion documentation shall explain:

- the orchestration lifecycle;
- separation between submission, confirmation and execution;
- dependency injection;
- composite workflow audit events;
- deterministic audit ordering;
- partial audit persistence;
- lack of cross-system transactional atomicity;
- how adapters should call the orchestrator;
- why AI and user-interface code remain outside the deterministic core.

## 20. Security and safety considerations

The orchestration service shall preserve the following safety properties:

- validation precedes confirmation-policy application and execution;
- approval never occurs implicitly;
- execution requires approved state;
- high- and critical-risk confirmation rules remain enforced;
- unexpected handler failures are contained by the existing execution
  boundary;
- audit failures are visible;
- partially persisted audit prefixes are reported;
- audit history is never repaired silently;
- injected dependencies define all external side effects;
- AI output cannot bypass deterministic validation and approval.

## 21. Known limitations

Milestone 1.7 shall not guarantee atomic commitment across:

- immutable proposal results;
- audit persistence;
- external handler side effects;
- future external databases or services.

A handler may complete an irreversible external side effect before a later
audit write fails.

A multi-event submission may persist a valid prefix before a later event
fails.

Future designs may require:

- idempotency keys;
- durable job records;
- transactional outboxes;
- compensating actions;
- retry policies;
- external side-effect reconciliation;
- a dedicated runtime coordinator.

These are outside the current milestone.

## 22. Acceptance criteria

Milestone 1.7 is complete because:

- `ActionOrchestrator` is implemented;
- submission, confirmation and execution are separate explicit operations;
- validation precedes confirmation-policy application and execution;
- execution is impossible before approval;
- existing workflow functions and audit factories are reused;
- duplicate audit representations are avoided;
- audit events are persisted in deterministic order;
- partial audit persistence is represented explicitly;
- orchestration dependencies are injected;
- clocks and audit-event identifiers are deterministic in tests;
- structured orchestration results are implemented;
- expected dependency failures are safely contained;
- operational documentation is complete;
- the README reflects the capability and limitations;
- all 419 automated tests and repository quality checks pass.
